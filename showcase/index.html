Project overview

What the shop is for, who uses it, and what the essay delivers.

The problem it solves

Before Họa. had a system, paintings were sold through social-media messages, a picture folder and two spreadsheets. Chapter 1 traces five problems to their root causes and the need behind each (§1.6 · p. 10, problem tree); every requirement of the essay attacks one of these causes.

P1

Customers cannot find a suitable painting

CauseSearch by title only; no descriptive attributes; photos and speech cannot be used

ImpactLost customers, long consultations

NeedFind paintings by description, voice, photo, or a photo of the room

P2

Sold-out prints are sold

CauseStock updated by hand, separate from orders

ImpactCancelled or late orders, lost trust

NeedAccurate stock at checkout time

P3

Customers do not know where their order is

CauseOrder status only in a staff spreadsheet

ImpactRepeated questions, overloaded staff

NeedSee and look up order status at any time

P4

Orders and prices handled by hand

CauseNo administration tool

ImpactWrong prices, slow delivery

NeedTools to manage paintings and order status

P5

Risk of leaking data

CauseCustomers identified by an order id in a message; card numbers written down

ImpactLegal risk, loss of trust

NeedOwnership checks, no stored card numbers, voice kept local

System goals

  • BO1Customers find a suitable painting faster, even when they do not know its titleTime and number of steps from the first query to the painting detail page
  • BO2More searches lead to a purchaseShare of search sessions with an “add to cart”
  • BO3Never sell a sold-out print, never charge a wrong priceNumber of orders cancelled because of stock or price errors
  • BO4Less staff time spent answering “where is my order?”Number of order questions answered by the system itself
  • BO5Protect customer and payment dataNo case of a customer seeing another customer's order; no full card number stored

  1. 1 → 2Analysis → Logical data model

    What changed

    Every class becomes «ORM-Persistable»; each relationship gets a name that reads as a sentence and a multiplicity at both ends; each generalization becomes an is a link 1 – 0..1; the «create» dependency of checkout is left out.

    Why

    The analysis diagram (§2.9 · p. 54) deliberately shows only the kind of each relationship. Before anything can be stored the analyst must say how many objects take part on each side, and the relational model has neither inheritance nor operations (§2.10.2 · p. 58).

    Benefit

    Every line now carries what a foreign key needs, so the tables can later be derived by rule instead of by taste.

  2. 2 → 3Logical data model → Design

    What changed

    Attributes become private and typed — money (amount, cartPrice, cashReceived, changeAmount…) becomes BigDecimal, dates LocalDate/LocalDateTime, free-text states the enumerations DetailKind, OrderStatus, ShippingStatus, PaymentStatus. Associations get a direction and a role name (customer, items, shipping, payments on Order). Behaviour arrives: addItem(), addPayment(), calculateTotal(), cancel(), advanceTo(), isOwnedBy().

    Why

    Design answers what each class holds, with which type, and which rule it owns (§4.3 · p. 103). Binary floating point cannot hold cents; an enumeration makes an impossible state unwritable; a direction is kept only where the code must ask the question.

    Benefit

    The rules live in the domain classes, not in one large service, and each rule is one method a test can call: the 13 “Domain rules (4.1, 4.3)” tests do exactly that.

  3. 3 → 4Design → Order.java

    What changed

    tools/gen_java.py writes one Java file per design class into demo/generated; the running code started from that skeleton and keeps every name. Role names become fields, operations become the methods below.

    Why

    The code is generated from the layered model, not written from memory (§4.5.1 · p. 122), so a renamed class or a missing method is a modelling decision, not an accident.

    Benefit

    check_code_model.py re-reads code, views and database on every build: Model check: 60 Java classes, 169 fields, 185 operations, 26 view functions, 18 tables, 91 columns, 62 SQL statements -> all match the model

  1. 1 → 2Conceptual → Logical

    What changed

    The entities gain their attributes and the «ORM-Persistable» stereotype; every named link gains multiplicities at both ends; generalizations become is a links.

    Why

    The conceptual level only fixes which things the shop must remember and how they relate; the logical level must say how many, before storage can be decided.

    Benefit

    Each multiplicity becomes something the database can enforce: a foreign key, a UNIQUE column or a composite key.

  2. 2 → 3Logical → Physical

    What changed

    Each persistent class becomes a «table» with SQL types and {PK, FK, U, NULL} markers; Order → orders (SQL keyword); generalization becomes class-table inheritance (customer_vip.customer_id → customer, customer_new.customer_id → customer); 1 – 0..1 links become a foreign key with UNIQUE (cart.customer_id, shipping.order_id); composed lines get a composite key (cart_item, order_item).

    Why

    The physical level is a design decision (§4.2.1 · p. 97): column types follow the typed design classes (BigDecimal → numeric) and the rules are applied mechanically by gen_sql.py.

    Benefit

    The database itself refuses impossible values: 6 of 6 statements that break a constraint were rejected in sql_validation.txt.

  3. 3 → 4Physical → Database (VP ERD)

    What changed

    The same tables, on the same grid, as a Visual Paradigm entity–relationship diagram: key icons, N and U markers, crow's-foot ends with the foreign-key names, solid identifying and dashed non-identifying relationships.

    Why

    The outline asks for the database to be generated in the modelling tool (§4.2.3 · p. 100); the ERD is Visual Paradigm's database view of the physical model.

    Benefit

    Cardinalities and identifying keys are visible at a glance and can be checked against the model: the exported SVG shows 18/18 tables and 66/66 column names of model.TABLES.

  4. 4 → 5Database (VP ERD) → Generated SQLite schema

    What changed

    gen_sql.py reads model.TABLES and writes the CREATE TABLE statements in foreign-key order (ecom_schema_sqlite.sql) and the seed (seed.sql); Database.initialize creates demo/data/ecom.db at the first start.

    Why

    Generated, not typed by hand, so the schema cannot drift away from the model.

    Benefit

    Loaded into SQLite 3.53.4 while this page was built: 18 tables, 91 columns and 19 foreign keys — identical to the model; the seed fills 154 rows.

    Benefit

  2. 2 → 3Analysis sequence (BCE) → Design sequence

    What changed

    The boundary becomes CheckoutController (customer id from the session), the control becomes CheckoutService.checkout(cartId: String, customerId: String, addressId: String, payment: Payment): Order, the entities answer with domain methods, and storage appears as repository interfaces.

    Why

    Lecture 05 gives four roles: the controller lets a request in, the service coordinates, the domain keeps the rules, the repository persists (§4.4.3 · p. 119).

    Benefit

    Every arrow is a method declared in tools/model.py; because the service depends on interfaces, the tests run it against a fresh SQLite database.

  3. 3 → 4Design sequence → Runtime

    Why

    The design sequence is the specification of the method; the essay walks through the same steps.

    Benefit

    9 “Checkout (slide A05)” tests run this exact path on a seeded database — all pass. Known limit: the stock decrease and the emptying of the cart follow the order transaction as separate statements (§5.12 · p. 146).

Products, their category and the detail tables

Every row of product points to exactly one category through product.category_id → category.category_id (“classifies”, 1 – 0..*).

category.detail_kind names the detail table that holds the specific attributes, so its category decides where the rest of a product lives: PAINTING → painting, FRAME → frame.

The detail tables use class-table inheritance: their primary key is also the foreign key to product (“is a”, 1 – 0..1), so a painting or a frame is one product row plus one detail row.

Other tables point at a product without being a kind of product: product_feature (indexed by), cart_item (refers to), order_item (refers to).

In the design model the class Category (domain.product) carries it with the enumeration DetailKind = PAINTING, FRAME and the operation Category.accepts.

Limitations (§5.12 · p. 146)

  • Attribute vectors instead of learned embeddings. The 28-dimensional vectors compare what Gemma reads, not how a painting looks; two very different blue landscapes are identical to the index. Image embeddings from a vision model, stored in a real vector database, are the next step.
  • Single machine. SQLite and an in-memory index fit the demo, not a shop with many simultaneous users. The repository interfaces allow another database without changes to the services.
  • Checkout is not one transaction. The order is saved in one transaction, but the stock decrease and the emptying of the cart are separate statements; a crash in between would leave a saved order with stock not yet decreased. Future work: wrap the three steps in one SQLite transaction.
  • Demo accounts and simulated payment. There are no passwords and no real payment gateway; the design keeps them outside the system boundary (Chapter 1).
  • Cancellation does not restore stock. OrderService.cancelOrder only changes the status; this was recorded as an open question in UC11. Future work: give ProductRepository the inverse operation of decreaseStock and call it when an order is cancelled.

Key design decisions

  • Declare every name once. tools/model.py is the only place where requirements, use cases, classes, methods and tables are written; diagrams, SQL, Java skeleton and essay tables are generated from it, so a change is made once and appears everywhere.
  • Three layers, one shared domain. Presentation → Application → Data with dependencies pointing down only; the domain classes are shared by all three (packages). The checker verifies the imports of every file.
  • Rules live in the domain. Order.cancel, Order.advanceTo, Order.isOwnedBy and OrderItem.fromCartItem hold the business rules; services only coordinate.
  • AI behind interfaces, always with a way back. LlmClient and SpeechClient hide Gemma 4 and Whisper; every AI feature has a rule-based path, so the shop works when the model does not.
  • Privacy as a requirement. The identity comes from SessionManager, never from the request; another customer's order looks exactly like a missing one; Whisper runs on the laptop so audio never leaves it.
  • Generated database with constraints. Class-table inheritance, foreign keys, UNIQUE and CHECK constraints generated by gen_sql.py, so the database itself refuses impossible data.

Conclusion

The essay follows one product through the five steps of the course, and this page shows that the steps are connected: each requirement has a use case, each use case its diagrams, each diagram the classes and tables it became, and each of those the lines of code and the tests that run them. The figures, the database and the code are generated from the same specification and checked against it on every build, the AI features are measured and can fail without breaking the shop, and the limits that remain are written down rather than hidden.
